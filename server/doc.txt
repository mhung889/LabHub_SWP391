UC-01 – LOGIN
Field
Description
Use Case ID
UC-01
Use Case Name
Login
Primary Actor
OJT, Mentor, Student
Description
Allows a user (OJT, Mentor, or Student) to authenticate into the Lab Internship Management System using email and password. The system validates the credentials, checks account status, and establishes a login session with the correct role and permissions.
Preconditions
- The user account has been created in the system with a valid email, password, and role (OJT / Mentor / Student).
- The account is not locked or disabled.
- The user is currently not logged in on this device/session.
Postconditions
- A valid authenticated session is created for the user.
- The system knows the user’s role and permissions (OJT / Mentor / Student).
- The user is redirected to the Homepage (UC-04).
Trigger
The user browses to the application URL and opens the Login screen.
Normal Flow
1. The user opens the Login page.
2. The system displays the login form with the following input fields:
  - Email (required, text, format: valid email, max 100 chars).
  - Password (required, password type, min 8 chars, max 64 chars).
  - (Optional) “Remember me” checkbox (boolean).
3. The user enters email and password, optionally checks “Remember me”.
4. The user clicks [Login] button.
5. The system performs front-end validation:
  - If Email is empty, mark field as error “Email is required”.
  - If Email format is invalid, error “Invalid email format”.
  - If Password is empty, error “Password is required”.
 , If any front-end validation fails, the system does not send request to server and displays validation messages.
6. If basic validation passes, the system sends a Login API request containing:
  - email
  - password
  - device / browser info (optional, for audit).
7. The server receives the request and performs backend validation:
  - Check if an account with this email exists and is not soft-deleted.
  - If no user found, return error “Account not found”.
  - If user exists, verify hashed password.
  - Check if account status = Active (not Locked, not Suspended).
8. If all checks are valid, the system:
  - Generates an access token / session ID.
  - Loads user profile and role(s): OJT / Mentor / Student.
  - Stores session in server / token store.
  - If “Remember me” = true, issues longer-lived refresh token / cookie.
9. The system logs a successful login entry (userId, timestamp, IP, device).
10. The system returns success response and redirects the user to Homepage with proper role-based menu and permissions.
Alternative Flow
4a. User presses Enter instead of clicking [Login]
- The system treats it the same as clicking [Login] and continues from Step 5.

7a. Account is found but status = Locked / Inactive
- The system rejects login and returns message “Your account is locked. Please contact administrator.”
- No session is created.

7b. Password incorrect
- The system increments a failed login counter for this account.
- If failed counter < configured threshold, system returns: “Email or password is incorrect.”
- If failed counter reaches threshold, system may lock the account and inform user: “Your account has been locked due to too many failed attempts.”
Exception Flow
6e. Network error or server timeout
- The system shows a generic message: “Unable to connect to server. Please try again later.”

7e. Database error during user lookup
- The system logs the technical error internally.
- The system returns a user-friendly error: “Login failed due to system error.”
Non-Functional
- Passwords must be stored using secure hashing (e.g., bcrypt).
- Login response time under normal load: ≤ 3 seconds.
- System must protect against brute-force login attempts (account lockout, rate limiting).


UC-02 – CHANGE PASSWORD
Field
Description
Use Case ID
UC-02
Use Case Name
Change Password
Primary Actor
OJT, Mentor, Student
Description
Allows a logged-in user to change their current password to a new one. The system verifies the old password, validates the new password according to security policy, and updates it securely in the database.
Preconditions
- User is logged in (valid session).
- User account is Active (not locked, not deleted).
Postconditions
- User’s password is updated in the system.
- Any existing sessions/tokens may be invalidated according to security policy (optional).
Trigger
User selects “Change Password” from profile or account settings menu.
Normal Flow
1. The user opens the Change Password screen.
2. The system displays the form with fields:
  - Current Password (required, password type).
  - New Password (required, must follow policy: e.g. ≥ 8 chars, include uppercase/lowercase/digit/special).
  - Confirm New Password (required, must match New Password).
3. The user fills in all fields and clicks [Save].
4. The system performs client-side validation:
  - All fields are required, show “This field is required” if empty.
  - New Password and Confirm New Password must match, show “Passwords do not match”.
  - New Password must satisfy complexity rules, show detailed hint if not satisfied.
5. If validation passes, the system sends change-password request including:
  - userId (from session).
  - currentPassword (encrypted in transit).
  - newPassword.
6. The server receives the request and verifies:
  - The session/token is valid and not expired.
  - The currentPassword matches the existing hashed password.
7. If current password is correct and new password is valid, the system:
  - Hashes the new password with secure algorithm.
  - Updates the password in the User table/collection.
  - Optionally resets failedLoginCounter to 0.
  - Optionally invalidates other active sessions.
8. The system logs a password change event (but never stores raw password).
9. The system returns success message: “Your password has been changed successfully.”
10. Optionally, the system sends an email to the user: “Your password was changed at [time]. If this was not you, contact support.”
Alternative Flow
6a. Current password incorrect
- The system does not update password.
- Returns error: “Current password is incorrect.”
- May increase a “failed password change attempt” counter (for monitoring).

4a. New password same as current password
- The system rejects the request and shows: “New password must be different from current password.”
Exception Flow
7e. Database update fails (e.g., deadlock, connection loss)
- The system logs the technical error.
- Returns message: “Unable to change password due to system error. Please try again later.”
Non-Functional
- New password must be stored using strong hashing.
- Screen should not display password in clear text.
- Input fields must support “show/hide password” toggle for usability.


UC-03 – FORGET PASSWORD
Field
Description
Use Case ID
UC-03
Use Case Name
Forget Password
Primary Actor
OJT, Mentor, Student
Description
Allows a user who forgets their password to reset it via email. The system verifies the email, generates a secure token, sends a reset link, and allows the user to set a new password.
Preconditions
- User’s email is already registered and active in the system.
- SMTP/email service is configured and available.
Postconditions
- A reset token is generated, stored with expiry time (e.g., 30 minutes).
- If user completes the flow, the password is updated successfully.
Trigger
The user clicks “Forgot Password” on the Login screen.
Normal Flow
Phase 1 – Request Reset Link
1. The user clicks [Forgot Password] link.
2. The system opens a form with a single field:
  - Email (required, email format).
3. The user enters their email and submits.
4. System validates:
  - Email not empty.
  - Email format valid.
5. The system searches for a user with that email:
  - If exists and active, continue.
  - If not found, go to Alternative Flow 5a.
6. The system generates a secure random reset token and its expiry timestamp.
7. The system saves the token in database linked with userId and status = “Active”.
8. The system constructs a reset password link, for example:
  https://…/reset-password?token=XYZ.
9. The system sends an email to the user including:
  - Subject: “Password Reset Request”.
  - Body: greeting, instructions, reset link, expiry time.
10. The system shows a message: “If this email is registered, a reset link has been sent.” (avoid revealing whether email exists).

Phase 2 – Reset Password via Link
11. The user opens email and clicks the reset link.
12. The system receives token and validates it:
  - Token exists.
  - Token status = Active.
  - Token not expired.
13. If token is valid, the system displays Reset Password form with fields:
  - New Password (required, policy rules).
  - Confirm New Password (required, must match).
14. The user enters new password and confirmation, then submits.
15. System validates passwords (required, complexity, matching).
16. If valid, the system:
  - Hashes new password.
  - Updates user’s password in DB.
  - Sets token status = “Used”.
17. The system displays success message and redirect option to Login page.
Alternative Flow
5a. Email not found or account inactive
- For security, the system still shows generic message: “If this email is registered, a reset link has been sent.”
- Internally, no token is generated.

12a. Token expired
- System marks token as “Expired”.
- System displays message: “Reset link has expired. Please request a new one.”

12b. Token already used / invalid
- System displays error: “Reset link is invalid.” and suggests requesting again.
Exception Flow
9e. Email sending failss
- System logs the error.
- Optionally informs user: “We could not send an email at this time. Please try again later.”

16e. Database update error when saving new password
- System logs the error.
- Returns: “Password reset failed due to system error.”
Non-Functional
- Reset token must be cryptographically secure and random.
- Token must expire automatically after configured time.


UC-04 – VIEW HOMEPAGE (ROLE-BASED DASHBOARD)
Field
Description
Use Case ID
UC-04
Use Case Name
View Homepage
Primary Actor
OJT, Mentor, Student
Description
Displays the role-based dashboard after successful login. For OJT, shows system-wide overview; for Mentor, shows assigned students and pending tasks; for Student, shows today’s schedule, attendance status, and assigned tasks.
Preconditions
- User is authenticated (UC-01 completed).
- User’s role and basic profile are loaded successfully.
Postconditions
- Homepage is rendered with widgets corresponding to user’s role.
- Navigation menu is initialized according to permissions.
Trigger
Successful login or user clicks on “Home” in the navigation menu.
Normal Flow
1. User logs in or clicks Home.
2. The system reads the current user role from session/token.
3. The system determines which dashboard layout to use:
  - OJT Dashboard.
  - Mentor Dashboard.
  - Student Dashboard.
4. The system loads necessary summary data depending on role:
  For OJT:
  - Total number of Departments, Mentors, Students.
  - Today’s attendance statistics (present, absent, late).
  - Number of pending evaluations, pending leave approvals (if any).
  For Mentor:
  - Count of assigned students.
  - Today’s attendance status of assigned students (e.g. who has not checked-in).
  - List of active tasks created by this mentor.
  For Student:
  - Today’s required working hours and check-in/check-out window.
  - Today’s attendance status (not yet, checked-in, checked-out, late).
  - List of assigned tasks with due dates.
  - Latest notifications.
5. The system renders the homepage view with:
  - Role-based navigation menu.
  - Dashboard widgets/cards.
  - Quick links (e.g. “Check-in now”, “View tasks”, “View leave requests”).
6. User can interact with widgets (click to go to detail screens).
Alternative Flow
4a. Some dashboard data sources return empty
- The system still loads the page but shows “No data” placeholders for those widgets.
Exception Flow
4e. Error when fetching dashboard summary data (e.g. DB timeout)
- The system logs the error.
- The system may show partial data and display a warning message like: “Some dashboard information could not be loaded.”
Non-Functional
- Homepage should load within 5 seconds under typical load.
- Dashboard API calls should be optimized with caching / pagination where appropriate.


UC-05 – VIEW USER LIST (ADMIN VIEW)
Field
Description
Use Case ID
UC-05
Use Case Name
View User List
Primary Actor
OJT
Description
Allows the OJT (admin) to view the complete list of users (Students and Mentors) in the system, with essential information and basic paging/sorting to support management operations.
Preconditions
- OJT is logged in with admin privileges.
- User data (Mentor & Student accounts) already exist in the system.
Postconditions
- A paginated list of users is displayed.
- The list can be further filtered or searched by other use cases (Filter User by Role, Search User).
Trigger
OJT selects “User Management, User List” from the menu.
Normal Flow
1. OJT clicks User List in the navigation menu.
2. The system sends a request to retrieve users with default parameters:
  - page = 1, pageSize = default (e.g. 20).
  - no filter, no search keyword.
3. The system queries the database for users and returns a collection of records containing at least:
  - userId (internal ID).
  - fullName (required).
  - email (required, unique).
  - role (required: STUDENT or MENTOR or OJT).
  - departmentName (optional, for Mentor and Student).
  - status (required: Active / Locked / Inactive).
  - createdDate (required).
4. The system calculates pagination metadata:
  - totalRecords, totalPages, currentPage, pageSize.
5. The system renders the User List grid with columns such as:
  - Name, Email, Role, Department, Status, Actions (View / Edit / Delete / Lock).
6. OJT can:
  - Scroll/paginate to other pages (Next / Previous).
  - Click a row to open View User Detail (UC-08).
  - Open other actions like Edit, Remove, Lock depending on permissions (UC-09, UC-… later).
Alternative Flow
3a. No users found (fresh system)
- System returns empty list and shows a message like “No users found. Please add new users.”
Exception Flow
3e. Database query error or timeout
- System logs technical details.
- System shows an error banner “Cannot load user list at the moment. Please try again later.”
Non-Functional
- User list must support pagination for performance.
- Sorting by name, email, role, status should be supported (may be detailed in an extended UC if cần).

UC-60 – SEND NOTIFICATION (MENTOR, OJT)
Field
Description
Use Case ID
UC-60
Use Case Name
Send Notification
Primary Actor
Mentor, OJT
Description
Allows Mentor or OJT to send notifications to one or multiple Students for announcements, task updates, leave responses, or system notices.
Preconditions
- User is logged in as Mentor or OJT.
- At least one Student exists in the system.
Postconditions
- Notification records are created for all selected Students.
- Students receive notifications in real-time or near real-time.
Trigger
Mentor or OJT clicks “Send Notification”.
Normal Flow
1. Mentor/OJT opens Send Notification screen.
2. The system displays input fields:
  - recipientType (required: Individual / Group / Department / All).
  - recipientIds (required if Individual/Group).
  - departmentId (required if recipientType = Department).
  - title (required, max 200 chars).
  - message (required, max 1000 chars).
  - relatedEntityType (optional: Task / Leave / Evaluation).
  - relatedEntityId (optional).
3. Sender fills in all required fields and clicks Send.
4. The system validates:
  - At least one recipient selected.
  - Title and Message are not empty.
5. The system creates notification records for each target student with fields:
  - notificationId.
  - studentId.
  - title.
  - message.
  - senderType (Mentor/OJT).
  - senderId.
  - createdDate.
  - isRead = false.
6. The system pushes notification to students via real-time channel (WebSocket/Push) or polling mechanism.
7. The system displays success message to sender.
Alternative Flow
4a. No recipient selected, system blocks submission and displays validation error.
Exception Flow
5e. One or more notification insert operations fail, system logs error and displays partial/failed send warning.
Non-Functional
- Max recipients per send must be controlled to avoid performance issues.
- Notification delivery latency should be < 5 seconds under normal conditions.
